## 1. 한눈에 보기

본 프로젝트는 Claude Code가 코드를 정확히 이해하도록, **계층형 컨텍스트 파일(CLAUDE.md)** 을 설계해 운영한다.

| 항목 | 값 |
|------|-----|
| 실사용 CLAUDE.md 파일 수 | **16개** |
| 총 분량 | **약 2,854줄** |
| 계층 깊이 | **3단계** (루트 → 레이어 → 도메인) |
| 핵심 설계 원칙 | "코드가 말하지 못하는 것만 적는다" |

**한 줄 요약**: 디렉토리 구조나 함수 시그니처처럼 *코드를 읽으면 아는 것*은 적지 않고,
함정·결정 이유·불변 규칙처럼 *코드만으로는 알 수 없는 것*에 집중해 계층적으로 분산 배치했다.

## 2. 계층 구조

컨텍스트 파일을 **상위는 인덱스, 하위는 세부**로 나누는 3단 계층으로 구성한다.
같은 정보가 두 곳에 중복되지 않도록, 상위 파일은 하위를 *가리키기만* 한다.

```
CLAUDE.md (루트, 142줄)  ─ 제품·스택·전역규칙 + 하위 인덱스
│
├── docs/api/CLAUDE.md  (55줄)   ─ API 계약 관리 규칙
├── docs/db/CLAUDE.md   (201줄)  ─ DB 스키마·마이그레이션 규칙
│
├── backend/CLAUDE.md   (387줄)  ─ 백엔드 공통 아키텍처·패턴
│   └── {도메인}/CLAUDE.md        ─ 도메인별 함정 (7개)
│       ├── auth(85)  user(64)  store(175)  community(135)
│       └── record(104)  report(158)  chatbot(119)
│
└── frontend/CLAUDE.md  (374줄)  ─ 프론트 공통 패턴·컴포넌트 규칙
    └── features/{도메인}/CLAUDE.md  ─ 기능별 흐름·함정 (4개)
        ├── map(240)  community(163)
        └── record(283)  chatbot(169)
```

### 계층별 역할 분담

| 계층 | 파일 | 담는 것 | 안 담는 것 |
|------|------|---------|-----------|
| **1단 루트** | `CLAUDE.md` | 제품 정의, 기술 스택, 전역 불변 규칙, 하위 인덱스 | 도메인 상세 |
| **2단 레이어** | `backend·frontend/CLAUDE.md` | 공통 아키텍처, 코딩 패턴, 타입 매핑 | 개별 도메인 로직 |
| **3단 도메인** | `{domain}/CLAUDE.md` | 그 도메인 고유의 함정·결정·흐름 | 다른 도메인 규칙 |
| **횡단 문서** | `docs/api·db/CLAUDE.md` | 계약·스키마 *관리 규칙* | 스펙·스키마 전문(별도 파일이 원천) |

## 4. 내용 구성: 무엇을 적었나

계층마다 역할이 다르므로 **내부 섹션 구성도 계층별로 다르다.** 아래는 각 계층의 실제 구성이다.

### 4-1. 루트 계층 — `CLAUDE.md` (142줄)

프로젝트의 진입점. 매 작업마다 로드되므로 "전체에 걸치는 것"만 압축해 담는다.

| 섹션 | 담는 내용 | 성격 |
|------|-----------|------|
| `## 구조` | 큰 디렉토리 덩어리와 역할 | 지도 |
| `## 명령어` | 개발 서버 실행 / 검증 / DB 접속 / 크롤러 | 실행 |
| `## 포트 맵` | 서비스별 포트 표 | 참조 |
| `## 전역 규칙` | 프로젝트 전체 불변 규칙 (응답 래퍼·인증·모바일 퍼스트 등) | **규칙** |
| `## 주요 컨텍스트` | 하위 CLAUDE.md·핵심 문서로 가는 **인덱스 표** | **포인터** |
| `## 필수 외부 설정` | repo 기본값 없는 환경변수 | 설정 |
| `## 작업 흐름` | 스키마·API·검증의 선후 순서 | 절차 |

> 핵심은 `## 주요 컨텍스트` — "무엇이 어디 있다"만 적고, 그 내용은 하위 파일이 원천.

### 4-2. 레이어 계층 — `backend·frontend/CLAUDE.md` (387·374줄)

공통 패턴이 모이는 허리. **번호를 매긴 4블록**으로 일관되게 구성한다.

| 블록 | 질문 | backend 실제 섹션 | frontend 실제 섹션 |
|------|------|-------------------|--------------------|
| **1. 시스템 컨텍스트** | 무엇을 다루나 | 패키지 구조, DB 접속, 구현 API | 디렉토리·라우팅 구조, 환경변수 |
| **2. 행동 지침** | 어떻게 작성하나 | 레이어·Entity·DTO 패턴, 코드 스타일, **DO/DON'T** | apiClient·AuthGuard·Zustand 규칙, 디자인 시스템, **DO/DON'T** |
| **3. 메모리/참조** | 코드가 못 말하는 것 | 타입 매핑 표, 이미지 저장 구조, 스키마 현황 | Store 목록, 프록시 설정, normalizer 출력 |
| **4. 워크플로우** | 어떤 순서로 | "새 도메인: SQL→Entity→Repo→Service" | "새 기능: 폴더→Page→훅→라우트" |

> 두 레이어 파일이 **같은 4블록 골격**을 공유해, 백/프론트를 오갈 때 구조가 예측 가능하다.

### 4-3. 도메인 계층 — `{domain}/CLAUDE.md` (11개, 64~283줄)

특정 도메인을 건드릴 때만 로드. 백엔드와 프론트가 관심사가 달라 **구성이 살짝 다르다.**

**백엔드 도메인** (예: `store` 175줄) — API 중심:
```
파일 구성        — DTO·서비스 책임 (비자명한 분담만)
API 목록         — 엔드포인트별 요청/응답/인증/특이사항
핵심 설계 포인트  — Native 쿼리, N+1 방지, 파싱 등 함정
규칙             — 이 도메인 한정 불변 규칙
```

**프론트 도메인** (예: `map` 240줄) — 흐름 중심:
```
아키텍처 원칙    — 인스턴스 관리, 좌표 규칙 등 깨지기 쉬운 불변
기능 흐름        — 커스텀 훅 책임 범위, 데이터 흐름도
주요 규칙        — Z-Index 계층, 컴포넌트 규칙
DO / DON'T       — "피할 것 → 대신 할 것" 쌍
```

> 공통점: 둘 다 **앞쪽은 구조 파악, 뒤쪽은 함정·규칙**으로 끝난다.
> 차이점: 백엔드는 *API 계약*, 프론트는 *데이터 흐름*이 중심축.

### 4-4. 횡단 문서 계층 — `docs/api·db/CLAUDE.md` (55·201줄)

코드 트리에 속하지 않는 계약·스키마의 *관리 규칙*. 스펙 전문은 별도 파일(`contracts.md`, `Script.sql`)이 원천이고, 이 파일들은 "그 문서를 어떻게 유지하나"만 담는다.

### 실제로 담은 "비자명한 정보" 사례

본 프로젝트가 컨텍스트 파일에 기록한, *코드만으로는 알 수 없는* 핵심 정보들:

| 종류 | 사례 | 왜 코드가 못 말하나 |
|------|------|---------------------|
| **함정·우회** | AI 서버 POST는 `HttpURLConnection` 사용 (RestClient는 바디 누락 422) | 코드는 "지금 이렇다"만, "왜 이렇게 안 했나"는 못 보여줌 |
| **불변 제약** | `userId`는 JWT에서만 추출 (바디 수신 금지) | 위반해도 컴파일은 됨 |
| **좌표 규약** | OpenLayers 입력은 `[lon, lat]` 순서 고정 | 반전해도 에러 안 나고 위치만 틀어짐 |
| **타입 매핑** | DB 컬럼명 ≠ Java 필드명 (brand_name↔name 등) | 매핑 실수가 런타임에야 드러남 |
| **결정 이유** | 커뮤니티 익명 / 카카오 Auth Code Flow 채택 | 코드엔 결과만 남고 이유는 안 남음 |
| **진실의 원천** | API 스펙은 `contracts.md`가 기준 | 어느 파일이 기준인지 코드는 안 알려줌 |

## 5. 설계 원칙

본 컨텍스트 파일 체계가 따르는 핵심 원칙.

1. **코드가 말하지 못하는 것만 적는다** — 트리·시그니처 복사 배제, 함정·이유에 집중
2. **규칙은 [무엇을]+[왜] 형태** — Claude가 새 상황에 일반화하도록 근거를 명시
3. **확정과 추정을 구분** — 원인 미상은 미상으로 표기해 미래의 재탐색 여지 유지
4. **계층 = 상위 인덱스, 하위 세부** — 동일 정보의 중복 배제로 갱신 일관성 확보
5. **제품 맥락을 상단에** — "무엇을·왜 만드나"가 "어떻게 짜나"보다 선행
6. **차분한 톤** — 과도한 강조어를 절제해 진짜 위험 규칙이 도드라지게

## 7. 결론

- **계층화**: 루트 1 + 레이어 2 + 도메인 11 + 문서 2 = 총 16개를 3단으로 분산
- **응집**: feature 패키지 단위로 컨텍스트를 묶어, 한 도메인을 건드릴 때 필요한 정보만 로드
- **비중복**: 상위는 포인터, 하위는 원천 — 같은 사실을 한 계층에만 둠
- **본질**: 분량(2,854줄)이 아니라 *내용의 비자명성*에 초점 — 코드가 못 말하는 것만 담음

> 이 구조는 Claude Code가 매 작업마다 **최소한의 토큰으로 최대한의 맥락**을 확보하도록 설계되었다.
